# 日音成分站与群聚看板：先绑定账号、认领旧资料，再整合分房

状态：讨论稿，待双方维护者确认。本文不代表功能已实现或已部署。

本次只新增方案文档及 README 入口，不修改程序、数据、接口、登录、bot 或部署配置；无需构建或部署。

## 首要问题：QQ 互联拿不到数字 QQ 号，旧资料无法自动对应

成分站用用户填写的数字 QQ 号查找成分档案；看板的 QQ 互联登录用 `App ID + OpenID` 识别授权身份，再关联看板自己的 `user_id`。这条登录流程不返回数字 QQ 号。因此，用户在两边使用同一个 QQ，也不能仅凭现有字段自动找出对应的成分档案。

QQ 官方的[获取 OpenID 说明](https://wiki.connect.qq.com/获取用户openid_oauth2-0/)及[用户资料接口](https://wiki.connect.qq.com/get_user_info/)列出了返回字段，后者包含昵称、头像等资料，不包含数字 QQ 号。看板的[身份契约](https://git.dan.tw/dan/qgroup/src/commit/0893eeda4ef046c3eca95be2c411cf5633525ac4/docs/identity-contract.md)也明确说明不取得 QQ 号码、群名片或群成员资格。

| 标识 | 表示什么 | 能否直接对应成分站旧资料 |
| --- | --- | --- |
| 数字 QQ 号 | 成分站用户自行填写的号码 | 可找到旧记录，但填写号码不证明拥有这个 QQ |
| OpenID | QQ 用户在某个应用里的身份标识，须与 App ID 一起使用 | 不是 QQ 号，也不能跨不同 App ID 直接比较 |
| UnionID | 同一开发者名下按规则打通的应用间身份标识 | 不能假设两个独立项目天然相同，也没有本提案可依赖的「数字 QQ 号转 UnionID」接口 |
| 看板 `user_id` | 看板自己的稳定账号 ID | 可作为绑定后的对应键，但公开 ID 本身不是身份凭证 |

看板已有保存 UnionID 的代码，但仍按 OpenID 查找站内账号，不自动合并账号。即使两边以后满足 UnionID 打通条件，成分站只有数字 QQ 号的旧记录仍需认领，不能因此直接转换。参见 [QQ 官方 UnionID 说明](https://wiki.connect.qq.com/unionid介绍/)及上述看板身份契约。

建议的顺序是：**确认两边账号的控制权 → 认领或纠正旧成分档案 → 建立稳定对应关系 → 再接报名名单和分房建议。** 不把拿到数字 QQ 号、统一登录或合并仓库作为前置条件，也不按昵称、头像或手填 QQ 自动合并。

## 第一阶段：账号绑定与旧资料认领

### 本人确认两边账号

建议先实现一次性绑定流程，不要求成分站重新接入同一套 QQ 互联应用，也不要求看板取得数字 QQ 号。以下流程是待实现设计，不是现有接口：

1. 用户在成分站选择已有档案，使用原账号口令重新验证。不能只凭前端传来的 QQ 号、本地登录标记或公开档案 ID 发起有效绑定；没有原口令或存在争议时转入旧资料认领。
2. 成分站后端建立短时、一次性的绑定请求，关联本次会话和目标档案，然后引导用户到看板登录并确认目标账号。看板只接受固定登记的回调地址，并核对请求与当前会话。
3. 用户核对两边账号和将关联的档案，明确确认。双方通过后端校验绑定凭证并取得稳定账号 ID，不能相信浏览器直接提交的目标 `user_id`；验证取消、过期或账号切换时不建立关系。
4. 后端检查双方是否已有其他有效关联，成功后保存一对一关系；冲突时停止并展示处理入口，不覆盖旧关系。凭证只使用一次，重复请求不产生重复绑定；双方结果不一致时保持待核对，不能单边标成已完成。
5. 在两站提供查看和解除关联的入口。解除须重新验证操作账号，并同步停止使用旧对应关系；账号注销后也应失效。重新绑定重新验证，不按昵称自动恢复。

双方各自验证账号，不互传口令、登录 Cookie、QQ access token 或 App Key。绑定凭证只用于该次账号关联，不进入普通活动链接、导出文件或日志，也不能获得报名、分房或财务操作权限。现有合作方只读密钥不能代替这个流程。

**绑定只证明用户能够操作这两个账号，不证明成分站手填的 QQ 号等于本次授权登录的 QQ。** 如果群内需要进一步确认数字 QQ 号或群成员资格，应另设本人验证或管理员核对，不把绑定结果标为「QQ 号已由腾讯验证」。

### 旧资料如何认领和纠错

| 旧资料情况 | 建议处理 |
| --- | --- |
| 原口令可用，档案和现有对应没有争议 | 验证原账号后展示待认领档案，由本人确认并完成看板绑定；保留原喜好数据 |
| 无原口令、原记录未设口令，或仅知道 QQ 号／昵称 | 不因知道公开信息而允许接管；交管理员通过已有可信联系核对，再走受控恢复及本人确认；无法核实则保留未认领 |
| QQ 号填错，或同一人有多份档案 | 先确认档案归属并修正标识；展示需要保留的词条及熟悉度，由本人核对。保留原记录和变更依据，不静默拼接或覆盖喜好 |
| 一份档案被多个账号认领，或一个看板账号对应多份档案 | 暂停新增关联及有争议的自动匹配，保留已有数据，待本人和管理员核对；不能以最后一次填写为准 |
| 已有管理员填写的 `boardUserId` | 保留为历史人工对应并记录来源，逐步请本人确认；无争议记录可按原策略过渡使用，但不能自动标为本人已绑定 |
| 看板代报同行没有 `user_id` | 继续保留本场报名；先在看板按其原流程认领，再关联成分。不能借用代报者的账号或成分 |

建议为成分档案增加独立、稳定的 `profile_id`，让关联保存为 `profile_id ↔ 看板 user_id`，QQ 号作为可纠错的资料字段。该字段及迁移尚未实现；未来实施前应备份并验证旧资料保留和回退，不在本次文档 PR 中迁移数据。

关联记录应能区分「历史人工对应」「本人绑定」「存在争议」「已解除」，记录确认方式和必要的变更时间，不保存验证密钥。账号关联不合并看板账号，不修改历史报名、付款归属或账单。不能完成认领的人仍可使用原有功能，在整合流程中显示「未关联／待核对」，不伪造其成分或自动抢占旧档案。

本阶段的验收目标是：同一人只需确认一次；忘记口令、填错号码、重复档案、错误关联和退出使用都有明确处理路径。双方确认这些规则后，再讨论下面的名单和分房整合。

## 绑定后的数据与权限边界

后续使用流程为「看板报名 → 查看参加者喜好 → 生成分房建议 → 发起人确认安排 → 按实际包间结算」。建议由看板保存正式安排与结算，成分站提供音乐喜好和分房建议；重新计算不自动改动正式安排。

| 数据或操作 | 由谁保存或决定 |
| --- | --- |
| 活动时间、地点、报名、退出、候补递补 | 看板 |
| 音乐词条、熟悉度、相似度及建议算法 | 成分站 |
| 分房建议与调整中的草稿 | 成分站；导入看板后仍是待确认草稿 |
| 正式预分、房名、付款人及历次安排 | 看板，由当前发起人按既有权限保存 |
| 实际包间、费用、付款及退款 | 看板，沿用原结算与账本规则 |

合作方密钥继续只用于后端读取公开活动。导入和保存由看板已登录的发起人操作；不能把合作方密钥、QQ 号、成分站登录状态或文件里的 ID 当作看板操作授权。

首版不共用数据库，不交换密码、Cookie、OpenID 或 UnionID，不同步款项与私人备注。邀请活动及草稿仍不在既有合作方 API 的范围内。文档和示例不包含真实群友资料或密钥。

## 绑定后的名单及分房规则

1. **账号与报名分别识别。** `user_id` 用于跨活动对应成分档案；`attendee_id` 用于本场名单与分房。同名不合并，改名不产生新人，不能用昵称代替 ID。导出建议使用报名 ID，不带 QQ。
2. **未认领同行保留位置。** `user_id=null` 的同行不能使用代报者的成分。首版可手动分房；如果增加单场人工对应，应以 `event_id + attendee_id` 限定范围。
3. **没有成分不等于不合拍。** 所有人都保留在名单及包间中；无资料者标为「暂无成分」，不以零分代表不合拍。房间显示总人数及可计分人数，分数只描述有资料的成员。
4. **正式、候补、待确认分开。** 建议默认按正式报名者生成分房，候补及待确认者另列。发起人可明确选入候补预分，但分房不代表取得正式名额。安排的 `confirmation_state` 单独显示，不能与报名 `status` 混用；已拒绝安排者需核对。
5. **重新计算不覆盖正式安排。** 有人退出、递补或修改成分时，提示更新建议，由发起人核对差异后决定是否采用。
6. **喜好相似度只作参考。** 听过不等于会唱。保留手动调整；「想唱的歌」「与朋友同房」等条件可另行讨论，不作为首版必要范围。
7. **标清建议、预分和实际。** 看板已有 `actual` 时显示实际安排；即使 `actual.rooms=[]`，也不回退为旧预分。此规则沿用看板现有契约。

只有符合第一阶段确认及冲突处理规则的对应关系才用于自动匹配；历史人工对应明确标示来源。无对应或存在争议的报名者保留在完整名单中，等待认领或手动安排。

## 第二阶段：按已确认的对应关系读取完整名单

主要由成分站侧完成，所需看板入口由双方确认：

- 两站互相提供入口，能从某场看板活动进入对应的成分分析；链接只携带公开活动 ID。
- 按 `next_offset` 处理活动分页，优先用单场详情获取同一快照的名单和包间。
- 保留未关联者与同行，清楚显示报名状态、成分填写情况、计分覆盖人数及数据取得时间。
- `404` 或完整同步成功后消失的活动停止展示；`401`、`503` 及网络失败不能当作活动删除。不能只靠 `revision` 跳过重读，因为改名和账号注销未必令其递增。

这一步完成后，群友能看清一场活动有哪些人、哪些人的成分可参与计算；未关联者仍可参加活动。报名与正式安排以看板为准。

## 第三阶段：导出分房建议，在看板预览并确认

建议先通过 JSON 文件传递建议。成分站实现导出，看板实现导入预览，双方共同确认格式与验收；只完成其中一边不代表整条流程可用。现有合作方只读 API 不增加写权限。

以下为建议文件的最小字段，名称和格式均待讨论，**不是现有接口或已实现功能**：

| 字段 | 用途 |
| --- | --- |
| `schema_version` | 建议文件格式版本；不支持的版本拒绝导入 |
| `event_id` | 指定单场活动，禁止跨活动套用 |
| `source_event_revision`、`generated_at` | 记录生成时的活动版本和时间，供核对；不是授权或有效性证明 |
| `participants` | 生成时的完整有效报名快照：`attendee_id`、可为 null 的 `user_id`、`status`、`confirmation_state` |
| `rooms` | 建议房名及 `attendee_ids`；不携带付款人、费用或正式 room ID |
| `unassigned_attendee_ids` | 未分配者；与房间成员合计须覆盖文件中的完整名单，且每人只出现一次 |

成分站应保留从报名记录到成分档案的对应关系，计算后转换为本场 `attendee_id`。没有成分、未选入计算或暂不安排的报名者仍列入快照及未分配名单，不能在导出时丢失。

建议看板按以下步骤接收，具体实现需看板维护者确认：

1. 由当前活动发起人选文件，限制文件大小、房间数及字段格式。名称按普通文字显示，文件全部内容视为不可信输入。
2. 重新获取当前活动和名单，检查活动 ID、重复／未知／遗漏报名 ID、版本及名单差异。文件中的账号与状态不能覆盖看板记录。
3. 有人退出、递补、认领或安排状态变化时，先显示差异并要求更新或核对草稿。即使 `revision` 相同，也核对当前名单与账号关联；保存前再次检查。
4. 显示待确认安排，保留无成分者和未分配者。发起人核对房名与人员，并在看板选择每间付款人，不能由成分推断付款责任。
5. 已有预分时，明确对应已有稳定 room ID 或建立新房间，不按名称自动认定同一房间。已有款项的 room ID 仍须保留。
6. 发起人明确确认后，沿用看板 `PUT /api/events/:id/rooms` 的原权限、协议、去重键及 `base_revision` 检查保存。有新变动则重新核对；已有账单时不通过导入预分绕过结算更正流程。

导入预览本身不写入安排、不改报名、不产生款项，也不发送群通知。保存后是否增加专门的安排通知作为独立需求讨论，不暗中改变 bot 行为。

## 后续可选：统一入口和一键传递建议

账号绑定与旧资料认领属于第一阶段。一键传递分房建议及统一入口可在前三阶段可用后再评估。若需要跨站传递建议或统一登录，另定相应授权方案；账号绑定不等于授权第三方替用户修改活动，不扩大现有只读密钥的权限。

统一登录、合并仓库、合并数据库及机器人直接操作不作为上述阶段的前置条件。后续功能 PR 分别评估部署影响；看板侧还需遵守其[发布与兼容性规则](https://git.dan.tw/dan/qgroup/src/commit/0893eeda4ef046c3eca95be2c411cf5633525ac4/docs/deployment-policy.md)。

## 后续实现的验收场景

以下为待执行的验收清单，本次纯文档 PR 没有执行功能验收：

- QQ 互联不返回数字 QQ 号、未取得 UnionID 或两个应用的标识不同时，仍可经双边账号验证完成绑定；不猜测或换算数字 QQ 号。
- 仅填写别人的 QQ／`user_id`、伪造前端登录状态、错用回调或重放过期凭证均不能绑定；取消、账号切换、并发冲突及双方中途失败不产生错误的有效关联。
- 原口令可用、忘记口令、原记录无口令、号码填错、重复档案及争议认领均按第一阶段规则处理；历史人工对应不会自动变成本人确认；资料迁移保留原喜好及可核对依据。
- 本人能查看和解除关联；任一账号注销或解除后停止使用旧对应，不删除原成分或重写报名账务；重新绑定需重新验证。
